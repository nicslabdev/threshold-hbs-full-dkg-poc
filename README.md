# sha256-full-column-test

Proof of concept for the **full DKG** construction described in our
threshold hash-based signatures work: obtaining an entire CRV column
(all `N_STEPS` positions of one Winternitz hash chain) via MPC, with
**no dealer involved at all** — the trustees alone generate the
column and the real chain value at each position is never revealed
to anyone, not even transiently to a single party.

The run generates `N_COLUMNS` columns (default 4). The columns are
mutually independent — each one has its own fresh secret shares — and
are computed **sequentially**, one after the other, inside a single
MPC execution.

## The formula

For the base case (`i=0`), `CRV_0` is sampled independently at
random and published as-is. For `i ≥ 1`:

$$
\mathrm{CRV}_i = H\left(\mathrm{CRV}_{i-1} \oplus \bigoplus_{j=1}^{k} \mathrm{SK}_j^{i-1}\right) \oplus \bigoplus_{j=1}^{k} \mathrm{SK}_j^i
$$

where `SK_j^i` is the secret share held by trustee `j` at position
`i`.

## How to run it

```
docker compose up --build
```

`N_COLUMNS` is an input parameter of the run (default 4). Pass it in
the environment:

```
N_COLUMNS=8 docker compose up --build
```

or put it in a `.env` file next to `docker-compose.yml`:

```
N_COLUMNS=8
```

`N_STEPS` (default 16) and `NUM_PARTIES` (default 3) are still fixed
in `docker-compose.yml`.

Every party must agree on `N_COLUMNS`, so always set it for the whole
`docker compose` invocation rather than per service, and tear down
(`docker compose down`) between runs with different values — the
`Player-Data` inputs under `data/` are sized for the previous run.

## What to expect

Only `party0` prints locally (MP-SPDZ default behaviour in
non-interactive runs — the other parties still contribute their
shares to the MPC round, they just don't reveal the result to
themselves). You should see `N_COLUMNS` blocks headed
`--- Columna c ---`, each with `N_STEPS` lines `Reg[0] = 0x...`
printed in sequence — one full column, revealed one position at a
time. At the end, MP-SPDZ reports the total cost (time, data sent)
for the whole run.

Note that the circuit is fully unrolled at compile time, so
compilation cost grows linearly with `N_STEPS * N_COLUMNS`, and every
party compiles its own identical copy at the same time. Raising
`N_COLUMNS` too far will OOM-kill one of the containers during the
compile step (if `party0` is the one that dies, the others hang
retrying `getaddrinfo` on `party0` forever).

## Verifying correctness

`verify_full_column.py` recomputes the same columns independently in
plain Python (no MPC), using the same deterministic test inputs
generated by `entrypoint.sh`, so you can check the MPC output against
a trusted reference line by line. It takes the same parameters, so
pass the value you ran with:

```
python3 verify_full_column.py 8          # n_columns
python3 verify_full_column.py 8 16 3     # n_columns n_steps n_parties
```

It also reads `N_COLUMNS`, `N_STEPS` and `NUM_PARTIES` from the
environment, so `N_COLUMNS=8` set once applies to both the run and
the verification.
